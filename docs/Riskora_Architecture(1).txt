RISKORA — SYSTEM ARCHITECTURE
=================================

PRODUCT VISION
--------------
Riskora is a Security Visibility, Monitoring and Threat Detection SaaS for small and growing businesses.

The product does NOT aim to replace a WAF, firewall, EDR, SIEM or dedicated security team.
Its purpose is to help businesses:

1. Understand their public security posture.
2. Detect suspicious activity and possible attacks.
3. Group related events into incidents.
4. Alert the responsible team quickly.
5. Provide useful context and recommended actions.
6. Monitor their security posture continuously.

Core principle:
"Know when something is wrong with your digital security."

Riskora should initially focus on passive/public-domain assessment, monitoring and alerting. It should not actively exploit customer systems or attempt unauthorized attacks.

9. SECURITY EVENT MODEL
==================================================

A SecurityEvent represents an observed event.

Example:

timestamp:
2026-08-08 21:42

source:
185.x.x.x

endpoint:
/login

event_type:
AUTHENTICATION_FAILURE

metadata:
failed_attempt=true

The event itself is NOT automatically an attack.

The Detection Engine evaluates patterns.


==================================================
10. DETECTION ENGINE
==================================================

Initial rule-based detection.

Possible detections:

BRUTE FORCE
-----------
Many failed authentication attempts from one source.

CREDENTIAL STUFFING
-------------------
Many usernames/accounts with repeated authentication failures.

PATH ENUMERATION
----------------
Large number of requests to suspicious paths such as:
- /admin
- /wp-login.php
- /.env
- /phpmyadmin

RECONNAISSANCE
--------------
Repeated requests to discover application paths or infrastructure.

SQL INJECTION PATTERN
---------------------
Suspicious request patterns matching known SQL injection indicators.

XSS PATTERN
-----------
Suspicious request patterns matching common XSS indicators.

BOT / TRAFFIC ANOMALY
---------------------
Abnormal request volume compared with the normal baseline.

AUTHENTICATION ANOMALY
----------------------
Unusual authentication behavior.

DNS CHANGE
----------
Unexpected DNS configuration changes.

CERTIFICATE CHANGE
------------------
Unexpected TLS certificate changes.

IMPORTANT:
Detection should describe activity as suspicious or potentially malicious unless there is sufficient evidence to make a stronger claim.

==================================================

Riskora should monitor itself.

Organization:

- riskora.com
- api.riskora.com
- infrastructure
- Kubernetes cluster

- suspicious traffic
- incidents


==================================================
17. EXTERNAL MONITORING
==================================================

Riskora should NOT rely exclusively on itself to know if Riskora is down.

Use independent external uptime/health monitoring.

Flow:

External Monitor
       |
       | "Is Riskora available?"
       v
Riskora

If Riskora is completely unavailable:
External monitoring alerts the team.

This avoids the monitoring-system paradox.


==================================================
18. SECURITY PRINCIPLES
==================================================

- Monitor authorized assets.
- Start with passive/public security checks.
- Do not actively exploit customer systems.
- Do not claim certainty when only suspicious activity was detected.
- Validate all input.
- Rate limit APIs and scans.
- Use least-privilege credentials.
- Never commit secrets.
- Protect customer data.
- Separate organizations securely.
- Keep audit logs.
- Use HTTPS.
- Secure authentication.
- Add independent monitoring.
